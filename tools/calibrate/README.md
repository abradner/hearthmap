# tools/calibrate/

Proposes a calibration range (`dry`, `wet`, and a default `happy_min`/`happy_max`, in the
sensor's raw units) for each soil sensor from its history, writes them to `calibration.json` for
review and import in the editor, prints a report, and can merge the ranges into a config's soil
and plant pins as a **new** file.

Why: cheap capacitive probes disagree about what dry means. One reads 0% in a pot that is
merely dry, another 25%, a third reports raw ADC counts that *fall* as the soil gets wetter. A
raw `0` is a real reading, never missing data. Thirst is judged against each sensor's own range
(`schema/README.md`, `calibration`), and this tool finds that range from what the sensor has
actually done.

Python 3.11+, standard library only. Tests need `requirements-dev.txt`.

```sh
python3 tools/calibrate/calibrate.py propose --history tools/calibrate/examples/history.json \
    --out calibration.json --report report.txt
python3 tools/calibrate/calibrate.py merge --config my-config.json \
    --calibration calibration.json --out my-config.calibrated.json
```

Every example here is synthetic: `examples/history.json` is generated by
`examples/make_history.py` for the fictional flat's sensors, and `examples/calibration.json` and
`examples/report.txt` are the tool's output on it (a test keeps all three in step).

## Commands

| Command | Does |
|---|---|
| `fetch` | Home Assistant history -> a history file (so you can re-run offline) |
| `propose` | history file **or** Home Assistant -> `calibration.json` + report (stdout, or `--report FILE`) |
| `merge` | config + `calibration.json` -> a new config. Refuses to write over its input, even with `--force` |

Outputs are never overwritten without `--force`, and are written mode 0600: they hold entity ids
and, for `merge`, a house's config.

`propose` options: `--entity` (repeatable; narrows a history file), `--happy LOW HIGH` (default
`0.3 1.0`), `--valid-range MIN MAX` (raw values outside are physically impossible; default `0 100`
for sensors whose unit is `%`, none otherwise), `--polarity auto|normal|inverted`,
`--min-history-days` (default 7).

`merge` replaces `dry` and `wet` on every `soil` or `plant` pin whose `entities.moisture` has an
`ok` proposal. An existing `happy_min`/`happy_max` is kept if it still lies inside the new range
(and `happy_min` is not wetter than `happy_max`); otherwise, or with `--replace-happy`, the
default happy range replaces it. Pins of any other kind are skipped (moisture binds only to soil
and plant pins), and failed proposals leave their pin unchanged. Every pin's outcome is printed.
Review the result in the editor before using it.

## From Home Assistant

The tool reads a long-lived access token from an environment variable (`--token-env NAME`,
default `HASS_TOKEN`) or a file (`--token-file PATH`, which should be mode 0600). There is no
command-line option for the token: anything on a command line is visible to every user of the
machine and stays in shell history. The token goes only into the request's `Authorization`
header; it is never logged, put in a URL, or written to an output. A token with whitespace, control or
non-ASCII characters is refused before any request (without echoing it), any redirect from
Home Assistant is refused rather than followed (urllib would re-send the header to the new
address), and transport errors are reported from non-secret parts only. The tool never calls a
secrets manager itself.

Feeding it from a secrets manager for one command, with the 1Password CLI as the example (the
reference is a placeholder for your own item):

```sh
HASS_TOKEN="$(op read 'op://<vault>/<item>/<field>')" \
  python3 tools/calibrate/calibrate.py propose --ha-url https://homeassistant.example.test:8123 \
    --config my-config.json --days 28 --out calibration.json --report report.txt
```

The variable is set for that one command only. If the secrets manager is locked, `op read` can
print nothing and still exit 0; the tool then stops with "no Home Assistant token" rather than
sending an empty one. Use `https://` unless Home Assistant is on the same machine.

Entities come from `--entity` (repeatable) or `--config` (the `moisture` entity of every soil
and plant pin). The tool calls `GET /api/history/period/<start>?filter_entity_id=...&end_time=...&minimal_response`
once, for the last `--days` days (default 28).

## History file format

```json
{
  "version": 1,
  "units": { "sensor.example_basil_moisture": "%" },
  "sensors": {
    "sensor.example_basil_moisture": [
      ["2026-01-01T00:00:00Z", 41],
      ["2026-01-01T02:10:00Z", 40.5],
      ["2026-01-01T03:00:00Z", "unavailable"],
      ["2026-01-01T04:00:00+11:00", "39"]
    ]
  }
}
```

- `sensors`: entity id -> list of `[timestamp, value]`. Timestamps are ISO 8601 **with** a
  timezone (a naive timestamp is refused, not guessed). Order does not matter.
- A value is a number or a numeric string. Anything else (`"unavailable"`, `"unknown"`, `null`,
  `""`) is unavailable.
- `units` is optional: entity id -> Home Assistant unit. `%` turns on the 0..100 validity bounds.
- Like Home Assistant's recorder, a file may hold a sample only when the value changed: a value
  is taken to hold until the next sample (unavailable included), for at most 7 days.

## Method

1. **Clean.** Unavailable and physically impossible samples become gaps (a gap ends the previous
   value's hold).
2. **Despike.** A run of at most 3 samples that is far from the median of its neighbours (more
   than 5 scaled MADs and more than 10% of the sensor's span) *and* that the series leaves and
   comes back from is an outlier and is dropped. A step, such as a watering, does not come back,
   so it is never dropped.
3. **Refuse** when nothing can be said:
   - `no_valid_samples`;
   - `no_variation`: every valid reading is the same. A sensor stuck at exactly 0 is reported as
     "cannot calibrate: no variation (every valid reading is 0)", never given a zero-width range;
   - `insufficient_history`: fewer than 3 valid samples or less than a day.
4. **Flat-lines.** One value unchanged for more than 72 h mid-range is a frozen sensor and is
   left out of the percentiles and the drying rate. The same at the sensor's lowest or highest
   reading is kept and reported as **saturation** (`saturated_dry_end`/`saturated_wet_end`): the
   probe may not be able to read any drier (or wetter) than that.
5. **Polarity.** Watering is fast and drying is slow, so whichever direction has more sharp
   moves is "wetter". With no sharp moves, the direction the reading mostly drifts in is
   "drier" (reported as `polarity_from_trend`). `--polarity` overrides.
6. **Watering events.** A rise of at least 20% of the span (and at least 4x the noise) within
   3 h, timed from when the previous reading stopped being the latest one, so a watering recorded
   hours after the last change still counts. Consecutive rises within 3 h are one event.
7. **Range.** Evidence from events: the median **post-watering plateau** (the held value from
   1 h to 13 h after the peak, so overshoot has drained) and, with two or more events, the median
   **pre-watering trough** (the held value in the 3 h before the rise). A bound from the whole
   history: the 95th and 5th **time-weighted** wetness percentiles of the held values. `wet` is
   the wetter of plateau and 95th percentile, `dry` the drier of trough and 5th percentile, so
   top-ups of a still-moist pot cannot hide a week at 0%, nor partial waterings a thorough
   soak. `evidence.dry_method`/`wet_method` say which won. Wetness is polarity-aware: for an
   inverted probe `dry` is numerically above `wet`.
8. **Drying rate.** The median least-squares slope over each stretch between waterings at least
   12 h long, in raw units per day (positive = drying), and as a fraction of the range per day.
9. **Judge.** A range not wider than 4x the noise is `too_narrow`. Confidence: `high` with 3+
   waterings over 14+ days and no saturation or flat-line; `medium` with 1+ watering over 7+
   days; `low` otherwise (no waterings, or under 7 days).
    Values are rounded to about four significant digits of the range's width (never fewer than
    two decimals), so tiny raw units keep their range; a range that would still round to zero
    width is `too_narrow`.
10. **Happy range.** `happy_min` = dry + 30% of (wet - dry); `happy_max` = wet. A **default**,
    labelled as such in both outputs, to be tuned per species: `happy_max` below `wet` would warn
    "too wet" after every watering, and 30% matches the soil layer's default warn edge
    (`docs/decisions.md` D-028).

Each step is a function in `hearthmap_calibrate/analysis.py`; tuning knobs are the `Params`
fields there.

## calibration.json

`schema/calibration.schema.json`. One entry per sensor, in history order:

| Field | Meaning |
|---|---|
| `entity_id` | Matched against pins' `entities.moisture` on import |
| `status` | `ok`, or why not: `no_valid_samples`, `no_variation`, `insufficient_history`, `too_narrow` |
| `calibration` | Only when `ok`: `dry`, `wet`, `happy_min`, `happy_max`, the config's own calibration shape |
| `happy_is_default` | Only when `ok`: true, the happy range is the stated fraction, not species knowledge |
| `message` | Only when not `ok`: e.g. `cannot calibrate: no variation (every valid reading is 0)` |
| `confidence` | `high`, `medium`, `low`; `none` when not `ok` |
| `polarity` | `normal` (higher is wetter), `inverted`, or null |
| `watering_events` | Count |
| `drying_rate_per_day`, `drying_fraction_per_day` | Raw units per day and fraction of the range per day, or null |
| `warnings` | `{code, message}`: `unavailable_samples`, `impossible_samples`, `outliers_removed`, `short_history`, `flatline_ignored`, `polarity_from_trend`, `polarity_assumed`, `no_watering_events`, `one_watering_event`, `saturated_dry_end`, `saturated_wet_end`, `no_drying_trend` |
| `evidence` | Counts and intermediate values (informational; keys may change) |

The top level also carries `version` (1), `generated_at`, `generator` and the `parameters` used.

## Tests

```sh
python3 -m venv .venv && .venv/bin/pip install -r tools/calibrate/requirements-dev.txt
cd tools/calibrate && ../../.venv/bin/python -m pytest
```

Synthetic series with known answers (`tests/synth.py`): sawtooth watering cycles, noise,
overshoot, gaps, outliers, change-only recording, a sensor stuck at 0, one that only dries, an
inverted probe, a dry end saturating at 0, a frozen sensor; plus the file formats, the Home
Assistant client against a local HTTP server, token handling, the merge, and negative controls
for the schema.
